# Simulation World

A grid-based city simulation with two kinds of citizens:

- **Rule-based agents (48)** — Doctors, Teachers, Students, Shopkeepers and
  Office Workers. Behaviour comes from a fixed priority list in
  `app/ai/decision.py` (low energy → go home, high hunger → go eat, low
  happiness → go to the mall, low money → go to work/school, else idle).
- **Reinforcement-learning agents (10)** — `LearningAgent`s, each with its
  own tabular Q-learner (`app/ai/learning.py`) and its own memory. They
  choose from the same action space as the rule-based agents, but learn
  which action fits a given situation from reward feedback, with
  exploration (ε) decaying over time instead of following fixed rules.

58 citizens total, moving around a 30×30 grid of roads and buildings
(houses, a hospital, schools, offices, malls, restaurants, parks), reacting
to a day/night cycle, weather, tax hikes and road closures. Buildings are
placed at random, non-overlapping positions on every run, with a
reachability check that guarantees every building can actually be reached
on foot.

Backend and frontend are both complete and wired together end to end.

## Running it

```bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Then open `frontend/index.html` in a browser (or serve the `frontend/`
folder with any static file server). It connects to `ws://localhost:8000/ws`
and starts streaming live.

- `GET /` — health check
- `GET /docs` — interactive Swagger UI (auto-generated by FastAPI)
- `WS /ws` — connect here to start the simulation; the first connection
  triggers world generation (buildings, roads, all 58 citizens) and streams
  one JSON state frame roughly every 0.3s
- `POST /events/rain`, `/events/tax-hike`, `/events/road-closure` — trigger
  world events; the frontend's top-bar buttons call these

## Running the tests

```bash
cd backend
PYTHONPATH=. pytest
```

58 unit tests cover citizen models, buildings, pathfinding, the scheduler,
weather/tax/traffic events, the Q-learner (including its temporal-difference
update and exploration decay), reward/state logic, and the data each agent
exposes to the frontend inspector panel — all in isolation.

## Evidence the RL agents actually learn

```bash
cd backend
python evaluate_learning.py          # ~2 min; add --days/--seeds to shorten
```

This runs the real simulation headlessly for the same 10 agent slots under
three policies — random, the hand-written rules, and real Q-learning — over
many simulated days and several random seeds, then writes
`docs/learning_curve.png` and `docs/learning_results.json`.

Result (60 days, 5 seeds), measured on the fraction of agent-ticks with an
unmet need (energy < 30, hunger > 70, or money < 10) and a 0–100
well-being score (average of energy and 100 − hunger):

| Policy | % unmet needs (last 5 days) | Well-being (last 5 days) |
|---|---:|---:|
| Random | 99.7% | 10.5 |
| Rules | 22.2% | 46.4 |
| **Q-learning** | **13.4%** | **60.7** |

The reward value shown live in the frontend's "Avg. reward" panel is a
*training signal*, not an outcome measure — it rewards choosing the right
action while a need exists, not resolving it — so don't read it as a
scoreboard; the table above is the real comparison.

### How a tick works (`app/engine/simulation.py::step_simulation`)

1. Advance the clock, weather, tax state and road closures.
2. For each citizen: move one step along its current path and apply
   natural stat decay (`Citizen.advance()`).
3. Ask the agent what it wants to do next (`app/ai/brain.py::think()`):
   rule-based agents call `decide()`; `LearningAgent`s consult their own
   `QLearner`, which learns from the *previous* tick's transition now that
   this tick's true next state is known (`QLearner.observe()`).
4. If the action changed (or the agent has no path), resolve a target cell
   for that action — e.g. `go_restaurant` → nearest restaurant's entrance,
   `go_home` → the agent's own house — and path to it with A*.
5. If the agent has just arrived at its target, apply that action's effect
   once (e.g. `go_restaurant` reduces hunger and costs money, `go_work`
   pays a wage, reduced during an active tax hike).
6. Serialize the whole world state and send it over the websocket.

The real app and `evaluate_learning.py` share this exact function, so the
evaluation results describe the same code the live app runs.

### Buildings are solid obstacles

There's no doorway modeled — a building's own grid cell is never a valid
neighbor in `pathfinding.py`. Every place agents actually path *to* (homes,
workplaces, restaurants, malls) resolves to the nearest walkable cell next
to the building, not the building's own cell. Agents can still *start*
standing inside a building cell (their spawn point), since that only
matters for generating neighbors outward, not for being reached as a goal.

### Random building layout

Buildings are placed at random empty positions across the whole grid
(`_place_buildings_scattered` in `simulation.py`) rather than in fixed
regions, so the city looks different from the two-strip layout a naive
packing approach produces. After placement, a BFS from a known walkable
cell confirms every building is actually reachable; if a random layout ever
seals one off, placement fully retries (up to 20 times). The layout is
seeded (`random.Random(7)`), so it's reproducible across restarts.

### Population sizing and starting state

Occupation counts are sized against the capacity of the buildings placed on
the grid, so nothing wildly overshoots what the city can plausibly hold:

| Occupation | Count | Workplace type | Total capacity of that type |
|---|---:|---|---:|
| Doctor | 8 | hospital | 10 |
| Teacher | 8 | school | 40 (shared with students) |
| Student | 12 | school | 40 (shared with teachers) |
| Shopkeeper | 8 | mall | 30 |
| Office Worker | 12 | office | 100 (shared with learning agents) |
| Learning Agent | 10 | office | 100 (shared with office workers) |

Each citizen also starts with randomized energy/hunger/money instead of
identical values, so their needs don't all trigger on the same tick and
they don't all converge on the same building at once
(`_randomize_starting_stats` in `simulation.py`). Population generation is
seeded (`random.Random(42)`), so re-running produces the same
names/ages/starting stats each time — useful for reproducing a specific run
during review or debugging.

### Frontend notes

- **Agent inspector:** click any dot on the map for that citizen's live
  stats. Learning agents (gold dots) show an extra section with their
  current exploration rate, Q-table size, and last reward.
- **Stacked agents:** several agents sharing one grid cell (e.g. a dozen
  office workers at the same entrance) are drawn in a small grid inside
  that cell instead of on top of each other, and shrink as the pile grows.
- **Hover-freeze:** while the cursor is over the map, agent positions hold
  still so a moving dot can actually be clicked; the simulation keeps
  running underneath and resumes animating on mouse-leave.

## Known limitations / good next steps

- **No building occupancy enforcement.** `capacity` is stored on every
  building but nothing checks or limits how many citizens are "at" a
  building at once.
- **No Q-table persistence.** Each `LearningAgent`'s Q-table lives in
  memory only and resets when the process restarts. `evaluate_learning.py`
  is the way to get learning evidence without needing a long-running demo.
- **No death mechanic.** Hunger/energy can hit their extremes with no
  consequence beyond the stat sitting at the cap.
- **Happiness barely moves.** Only a mall visit raises it, and nothing in
  the simulation currently lowers it.
- **The reward function isn't an outcome measure.** It scores "chose the
  right action while a need existed," so a policy can score well without
  resolving the need. See the evaluation section above for the real
  comparison, and treat the live "Avg. reward" chart as a training signal.
